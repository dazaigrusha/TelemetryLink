# Частина 12 — доставка critical і діагностика

## Що змінено

До звітів додано взаємно виключні кінцеві стани кадрів: відновлено, не передано через бюджет, втрачено каналом, відхилено приймачем, збій декодера, неточне відновлення, не запаковано. Для всіх кадрів та окремо critical сума станів дорівнює кількості вхідних кадрів. NotPacked за штатного завершення нульовий.

Політика `critical-first` розділяє записаний сеанс на critical та звичайні кадри. Для critical діє межа **8 кадрів на пакет** (або менше, якщо вікно менше 8): це обмежує число критичних кадрів, які може забрати одна втрата. Звичайне вікно не обмежується додатково. Спочатку передаються всі critical-пакети; усередині черг використовується обраний scheduler. Звичайні кадри теж формуються в пакети, але можуть не поміститися в час.

Це обробка повного запису сеансу, а не онлайн-буфера з дедлайнами. Перестановка не змінює ознак MLP: класифікатор працює один раз на початковій часовій послідовності, а класи та цінність залишаються прив'язаними до оригінальних індексів. Формат, прапорці, HMAC, nonce та канал не змінені. Повторів або дублювання кадрів немає.

## Протокол перевірки

На seed 1001–1010 перевірявся початковий прототип окремих великих critical-пакетів. Він усунув бюджетні втрати, але показав ризик концентрації critical. Після цього введено фіксовану межу 8. Це обмеження не підбиралося random/GA і не гарантує оптимальності.

Після фіксації стратегії виконано порівняння **на 20 інших seed: 2001–2020**, усі три сценарії, по 3 повтори та 1 прогрів. Жодних подальших налаштувань за цими результатами не зроблено. Всього 360 виміряних прогонів; прогрів не входить у CSV. Повтори одного seed — не незалежні реалізації втрат; частка проходження порогу рахується по 20 seed. Три повтори описують часовий шум Q.

Конфігурація: huffman, dp, greedy scheduler, MLP із частини 9; --window 64, --threshold 0.5, --critical-weight 1. TRAIN/valid не використовувалися для змін або навчання. Змінюється тільки політика доставки: групування + розмір critical-пакетів + пріоритет черг.

|---|---|---|---|---|
| calm | balanced | 300.0 | 0.0 | 0.0 |
| calm | critical-first | 300.0 | 0.0 | 0.0 |
| working | balanced | 290.3 | 0.0 | 9.7 |
| working | critical-first | 290.0 | 0.0 | 10.0 |
| emergency | balanced | 108.2 | 173.0 | 18.8 |
| emergency | critical-first | 258.8 | 0.0 | 41.2 |

Відхилень, аварій приймача, невідповідностей і незапакованих critical у цих вимірах немає. Навіть зі строгою чергою втрати Маркова залишаються. Пріоритет змінює, які дані опиняються у втрачених пакетах, і може зменшувати доставку звичайних даних або погіршувати окремі запуски. Це потрібно оцінювати за таблицею, а не лише за середньою Q.

## Запуск

```bash
dotnet run --project src/TelemetryLink.Cli -- run --scenario emergency --delivery critical-first --classifier mlp --model EXPERIMENTS-S7/mlp.json --out results/critical.csv
dotnet run --project src/TelemetryLink.Cli -- compare --vary delivery=balanced,critical-first --scenario calm,working,emergency --seeds 2001,2002,2003,2004,2005,2006,2007,2008,2009,2010,2011,2012,2013,2014,2015,2016,2017,2018,2019,2020 --repeats 3 --warmup 1 --classifier mlp --model EXPERIMENTS-S7/mlp.json --out results/delivery.csv
```

Типовий режим CLI лишається balanced, щоб старі команди відтворювали попередню стратегію. Для critical-first потрібен явний прапорець. `run --strict` / `compare --strict` як і раніше повертають код 1, якщо поріг перевищено.

## Що перевірено тестами

Збереження всіх індексів рівно один раз, незмінність початкового порядку при класифікації, відповідність класів/цінності первинним індексам, відсутність змішаних пакетів, ліміт 8 critical, ліміт байтів, унікальні nonce, сумісність із чинним декодером, пріоритет черг навіть при зворотному scheduler, усі причини збоїв, нульовий/безcritical/повністю critical сеанси, детермінованість діагностики для того самого seed, експорт та помилкові CLI-значення. Дані, канал та приймальні тести викладача не змінені.

Далі — оцінка стратегій проти втрат каналу та підбір параметрів із контролем порогів на кількох seed. Збільшувати бюджет каналу або послаблювати пороги заради проходження не потрібно.
